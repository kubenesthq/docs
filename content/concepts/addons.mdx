# Addons

An Addon is a backing service: PostgreSQL, Redis, Kafka, Elasticsearch, RabbitMQ — anything that your application components depend on but that is not itself an application. In kubenest, addons are packaged as Helm charts and deployed into the project's namespace by the operator via ArgoCD, alongside your application workloads.

The key difference between an Addon and a Workload is what it produces. A Workload exposes a service to users (an API, a web UI, a background processor). An Addon produces **exports** — key-value outputs like connection URLs, hostnames, and references to generated credentials — that downstream Workloads consume.

That difference is why the concept exists. Without it, deploying a database is only half the work: someone still has to connect the consuming service to it. In kubenest the addon publishes connection details as exports, workloads declare which keys they consume, and the operator copies those export strings into their configuration. Secret-backed values and the current PostgreSQL DSN limitation still require the handling described below.

## Two entry points for addons

There are two ways to deploy an addon, depending on whether it should share an App's lifecycle or have an independent one. Standalone-to-App sharing is limited as described below.

### As a component in an App

The most common pattern is to include an addon as a component in the same App as the workloads that depend on it. The addon deploys, patches, rolls back, and deletes with the App. Pausing an App affects workload replicas only; the addon keeps running.

```json filename="addon as App component"
{
  "name": "postgres",
  "type": "addon",
  "addon_spec": {
    "type": "postgres",
    "chart": {
      "repo": "https://charts.bitnami.com/bitnami",
      "name": "postgresql",
      "version": "13.4.4"
    },
    "values": {
      "auth": {
        "database": "myapp",
        "username": "myapp"
      }
    }
  }
}
```

When deployed as a component, the operator manages the addon's Helm release as part of the StackDeploy reconciliation loop. The `depends_on` and `exportRef` wiring described in [Apps](/concepts/apps) applies here.

### As a standalone AddonInstance

You can deploy an addon as a standalone `AddonInstance`. Standalone instances have their own lifecycle, separate from any App.

```bash filename="create standalone addon instance"
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "project_id": "b2c3d4e5-...",
    "name": "shared-postgres",
    "definition_id": "def1uuid-...",
    "values": {
      "auth": {
        "database": "shared"
      }
    }
  }' \
  https://api.your-domain.com/api/v1/addon-instances
```

<Callout type="warning">
Standalone instances are not currently a working shared-export source for Apps. An inline `export_ref` with `addon_instance_id` passes request validation but fails in the backend's CRD conversion. `POST /api/v1/apps/{ns}/{name}/attach-addon?project_id=<UUID>` injects a component-name reference but does not add the corresponding addon component, so the operator rejects an App that does not already contain a same-name addon component.
</Callout>

## The AddonDefinition catalog

An `AddonDefinition` is a catalog entry: it declares the chart reference, the default Helm values, and the **export schema** — the set of keys the addon publishes after a successful deploy. Platform admins register AddonDefinitions; users reference them by ID when creating addon instances.

```bash filename="list addon definitions"
curl -H "Authorization: Bearer $TOKEN" \
  https://api.your-domain.com/api/v1/addon-definitions | jq .data[].name
# "PostgreSQL"
```

Using a definition rather than specifying a chart directly fixes the chart reference and supplies default values. Its export schema documents the intended keys, but the operator does not consume that schema during extraction; it selects the built-in `postgres`, `redis`, or `kafka` extractor from the addon's `type`, and uses the generic extractor for other types.

<Callout type="info">
You do not need to use a definition. If `definition_id` is omitted from the `AddonInstanceCreate` payload, you must supply `type` and `chart` directly. This is useful for one-off or custom addons that do not have a definition entry.
</Callout>

## Exports: how addons publish their outputs

After a Helm chart deploys successfully, the addon publishes its outputs as **exports** — a key-value map stored on the `AddonInstance` record. The standalone-to-App wiring limitation above applies to consuming those values.

What the `postgres` addon type publishes:

| Key | Example value |
|-----|---------------|
| `dsn` | `postgresql://myapp:${postgres-password}@shared-postgres-postgresql.my-project.svc.cluster.local:5432/myapp?sslmode=require` |
| `host` | `shared-postgres-postgresql.my-project.svc.cluster.local` |
| `port` | `5432` |
| `user` | `myapp` |
| `database` | `myapp` |
| `passwordRef.name` | `shared-postgres-postgresql` |
| `passwordRef.key` | `postgres-password` |

The operator also publishes conventional aliases for the same values, so a container that expects the standard PostgreSQL environment names can consume them without a mapping step: `DATABASE_URL` (an alias of `dsn`), `PGHOST`, `PGPORT`, `PGUSER` and `PGDATABASE`.

The password itself is not an export, and there is no export key that yields it. `passwordRef.name` and `passwordRef.key` name the Kubernetes Secret and the key within it; reading that Secret is the consumer's job.

<Callout type="warning">
**`dsn` and its `DATABASE_URL` alias are not usable connection strings today.** The password segment is a literal `${postgres-password}` placeholder — the name of the Secret key, not the password — and nothing substitutes it. The operator resolves an `exportRef` by copying the export value into the consuming container's environment verbatim, so the app receives the placeholder text and fails to connect.

This is a live defect, tracked as `kn-kgu5`. Until it is fixed, use `host`, `port`, `user` and `database`, which are plain values and resolve correctly, and read the password from the Secret yourself.
</Callout>

Exports are read from cluster resources after the chart completes. When exports are backed by a Kubernetes Secret, the API response returns the export keys and Secret reference but redacts the values. The read endpoint does not fetch or return those Secret values.

```bash filename="read addon exports"
curl -H "Authorization: Bearer $TOKEN" \
  https://api.your-domain.com/api/v1/addon-instances/$INSTANCE_ID | jq .exports
```

## Revision history and rollback

Every values update or chart version bump to a standalone addon instance is recorded as a **revision**. This gives you a full audit trail and the ability to roll back to any prior configuration.

```bash filename="update addon values"
curl -X PATCH \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "values": {
      "primary": {
        "resources": {
          "requests": { "memory": "512Mi", "cpu": "250m" }
        }
      }
    },
    "note": "Increase memory for production load"
  }' \
  https://api.your-domain.com/api/v1/addon-instances/$INSTANCE_ID
```

List revisions:

```bash filename="list revisions"
curl -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/addon-instances/$INSTANCE_ID/revisions" | jq .
```

Roll back to a prior revision by number or ID:

```bash filename="rollback"
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"revision_number": 1, "note": "Reverting memory increase"}' \
  https://api.your-domain.com/api/v1/addon-instances/$INSTANCE_ID/rollback
```

The rollback creates a new revision (it does not delete the intervening ones), so the audit trail remains intact.

## Addon phases

Standalone addon instances move through the same phase vocabulary as Apps:

| Phase | Meaning |
|-------|---------|
| `Pending` | Created; operator has not yet started the Helm install |
| `Deploying` | Helm install/upgrade in progress |
| `Running` | Helm release is deployed and healthy |
| `Failed` | Helm install/upgrade failed; error is on the revision record |

## Common pitfalls

**Deleting an addon instance.** The backend does not check Apps for dependencies before deletion. The current standalone-to-App wiring path is not functional, so do not rely on the backend to discover or protect external consumers.

**Chart version mismatches.** If you specify a chart version in an `AddonDefinition` and then try to deploy with a different version in the `values` override, the definition version takes precedence. Use `chart_version` in the PATCH request to explicitly upgrade.

**Export key names vary by addon type.** The keys above are what the `postgres` type publishes. Each recognized type (`postgres`, `redis`, `kafka`) has its own extractor and its own key set; any other type falls back to generic `service.url` and `service.port` exports. Check the addon definition's export schema to discover the available keys.
