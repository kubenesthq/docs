# Addons

An addon is a backing service: PostgreSQL, Redis, Kafka, Elasticsearch, RabbitMQ. Anything your
application depends on but that is not itself your application.

What separates an addon from a workload is what it produces. A workload serves users. An addon
produces **exports** — connection strings, hostnames, credentials — that workloads consume. That is
the whole reason the concept exists: without it, deploying a database is half the job and somebody
still has to wire the consumer to it by hand.

<Callout type="warning">
**Not supported by the current release.** The commands on this page — `kubenest deploy`
and `kubenest addon` — were removed from the command tree and are frozen scope
under decision D1. The released CLI installs and operates the platform only, so this callout comes
off only when a release that lifts that decision is promoted.

</Callout>

## In an app

The common case. A component with an `addon:` key is a backing service rather than a container, and
it lives and dies with the app:

```yaml filename="kubenest.yaml"
components:
  api:
    image: myorg/my-api:v1.2.0
    port: 8000
    env:
      DATABASE_URL: ${postgres.dsn}

  postgres:
    addon: postgres@16
    storage: 20Gi
```

`kubenest deploy` creates Postgres first because `api` reads a value from it, waits for the exports,
then starts `api` with a usable `DATABASE_URL` injected from a per-workload Secret. KubeNest resolves
the database password from the addon credentials into that Secret, so the app does not assemble a
connection string or read the database credentials itself. Pausing the app does not pause the addon —
databases keep running so data survives.

## Standing on its own

When several apps share one database, or when its life should outlast any single app:

```bash filename="terminal"
kubenest addon create shared-postgres --type postgres@16 --project acme-prod --storage 50Gi
```

Reference it from any app in the same project:

```yaml filename="kubenest.yaml"
env:
  DATABASE_URL: ${addon:shared-postgres.dsn}
```

## The catalog

```bash filename="terminal"
kubenest addon catalog
```

```ansi filename="output"
postgres     16, 15, 14    PostgreSQL
redis        7, 6          Redis
kafka        3             Apache Kafka
```

Each entry pins a chart, its default values, and the export keys it publishes. To run something the
catalog does not carry, name a chart directly:

```yaml
components:
  clickhouse:
    chart: oci://registry-1.docker.io/bitnamicharts/clickhouse
    version: 6.3.1
    values:
      auth:
        username: analytics
```

## Exports

What `postgres` publishes:

| Key | Example |
|-----|---------|
| `dsn` | `postgresql://myapp:…@shared-postgres.acme-prod.svc.cluster.local:5432/myapp?sslmode=disable` |
| `host` | `shared-postgres.acme-prod.svc.cluster.local` |
| `port` | `5432` |
| `user`, `database` | `myapp` |

The canonical PostgreSQL addon does not enable TLS inside the cluster, so its ready-to-use `dsn`
ends with `sslmode=disable`.

Conventional aliases come too, so a container expecting the standard PostgreSQL environment names
needs no mapping: `DATABASE_URL`, `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`.

Each type has its own extractor and key set. Anything else falls back to `service.url` and
`service.port`.

```bash filename="terminal"
kubenest addon show shared-postgres
```

```ansi filename="output"
shared-postgres   postgres@16   running   50Gi   revision 3

exports
  dsn        postgresql://myapp:••••@shared-postgres.acme-prod…
  host       shared-postgres.acme-prod.svc.cluster.local
  port       5432
  user       myapp
  database   myapp

used by
  my-api/api      DATABASE_URL
  my-api/worker   DATABASE_URL
  reports/etl     DATABASE_URL
```

<Callout type="info">
**Nothing ever prints a password.** Secret-backed values are redacted in every response and every
command. They are resolved on the cluster, at deploy time, into the consuming container — never
through the control plane and never onto your terminal. `kubenest addon password shared-postgres`
reads it from the cluster directly, when you genuinely need it.
</Callout>

## Changing one

Every values change or version bump is a numbered revision, so there is an audit trail and a way
back.

```bash filename="terminal"
kubenest addon set shared-postgres memory=1Gi --note "production load"
kubenest addon upgrade shared-postgres --to 17
kubenest addon revisions shared-postgres
kubenest addon rollback shared-postgres --to 2
```

A rollback creates a new revision rather than deleting the ones in between.

<Callout type="warning">
Rolling an addon back to an older chart version is a Helm **downgrade**. Helm will do it, but many
database charts run schema migrations on upgrade that do not reverse. Snapshot the data first —
`kubenest backup now` — before rolling back anything stateful.
</Callout>

## Deleting one

```bash filename="terminal"
kubenest addon destroy shared-postgres
```

It refuses while an app still references it, naming what depends on it. The volume goes with it, so
take a backup first if the data matters.

An addon that is a component of an app can be lifted out before you destroy the app, keeping the
data:

```bash filename="terminal"
kubenest addon detach my-api/postgres --as shared-postgres
```
