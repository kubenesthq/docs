# Profiles

<BuildStatus path="/platform/profiles" />

Core is what every cluster runs. Profiles are the only supported way to vary it.

A profile is a named, pinned set of components that is tested against core as a unit. You choose
profiles at install; the set is recorded against your cluster and travels with it through every
upgrade.

## What installs today

Core installs. No component profile does.

Ask for one — `--profile observability`, `--profile secrets` — and the installer refuses at
stage 11 rather than installing core in its place. Core is on the machines
by then: the cluster is marked `install-failed` in the control plane with `profiles` as the failing
stage, and the failure prints the same two exits every other stage does.

The refusal is deliberate, not a defect. Installing core while the record says
`core + observability` leaves a cluster that does not match its own record, and that record is what
every upgrade is planned against — so the installer stops rather than write something untrue.

<Callout type="warning">
**Re-running without the profile is not a resume.** The profile set is part of the install
journal's identity, so dropping the flag makes it a different install and the journal refuses to
resume into it. The way on is `kubenest platform uninstall --confirm` on those hosts, then a fresh
install of core on its own.
</Callout>

The `ha` tier is not affected by any of this. It is chosen with `--ha`, built by stage 3, and never
reaches stage 11 — what has and has not been run there is on [HA tiers](/platform/ha).

So today: install core, and take the profile you want when it ships. The rest of this page is the
design the two component profiles are being built to.

## Why profiles and not options

Because *N* independent on/off switches means 2<sup>N</sup> configurations, and nobody has tested
2<sup>N</sup> of anything.

Three switches would be eight combinations per release. Three profiles are **five**:

| # | Configuration |
|---|---|
| 1 | core alone |
| 2 | core + `observability` |
| 3 | core + `secrets` |
| 4 | core + `ha` |
| 5 | core + all profiles |

N+2, not 2<sup>N</sup>. The intent is that every one of the five is tested on every bundle release,
and it is the recurring cost of this entire strategy. A "tested bundle" that is not actually tested
in CI is a spreadsheet, not a product — which is why it is worth saying plainly that **the matrix
has not run yet**. No configuration has been through install, workload, backup, restore drill and
upgrade on a release. That is `kn-twe`, and until it runs, "tested together" is the design rather
than a claim.

The arrangement only holds because profiles are **largely orthogonal**: observability does not
interact with secrets. Anything that genuinely interacts belongs inside core *together* — which is
why storage and backup are both core, and why ingress and certificates are both core.

One place the orthogonality is not free is backup. A profile brings data with it — metrics and
logs for `observability`, the sealing key for `secrets` — and core's Velero is what would have to
protect it. So **each profile declares its own backup set**: the namespaces and labels that must
be captured, and anything, like a sealing key, whose loss is unrecoverable. The restore drill
covers what the profile declared, and its result names which profile's data it verified. That
makes orthogonality a property the drill tests rather than an assumption the matrix rests on.

**A profile name resolves to exactly one component set.** A slot that offered a choice — take
`secrets`, then pick either of two controllers — would mean the matrix could not say what
"core + `secrets`" was without picking one, and the count above would stop being a count. Where
two genuinely different answers are both worth offering, they are two profiles, not one profile
with a switch.

## The profiles

### `observability`

VictoriaMetrics, Grafana and Loki — metrics, dashboards and logs **for your workloads**.

VictoriaMetrics rather than vanilla Prometheus because it is meaningfully lighter for the same
query surface, and less weight is the product promise. The profile ships default dashboards for
cluster health, node resources, workload status and ingress traffic; a profile that installs three
components and no dashboards has not done anything.

Retention defaults are sized so the stack cannot quietly fill your disks.

<Callout type="info">
**This is not the fleet health telemetry in core.** That reports cluster state to your control
plane so problems are known before they are reported. This profile is your own observability, for
your own workloads. Different data, different audience. Neither replaces the other.
</Callout>

### `secrets`

Encrypted secrets in Git, so the GitOps flow works without plaintext credentials in a repository.

`secrets` is **sealed-secrets**, and only sealed-secrets: self-contained, no external dependency,
and it composes with the ArgoCD flow already in the product.

Clients who already run Vault or a cloud secret manager want external-secrets instead, which
integrates with what they have rather than forcing a second secrets system alongside it. That is
a second profile, `secrets-external`, and it is **not in the bundle today** — it lands, pinned and
tested, when a client who needs it arrives. One slot offering two controllers would make
"core + `secrets`" ambiguous in exactly the place the matrix has to be precise.

Vault is deliberately **not** offered as a default. It is a heavy operational commitment, and
precisely the kind of thing you are paying us to avoid.

<Callout type="warning">
**The sealing key is the most important thing in your cluster.** Lose it and every sealed secret
is unrecoverable. It is in the backup set for that reason. Key rotation and key backup are
documented on the backup and restore page.
</Callout>

### `ha`

Three control-plane nodes with embedded etcd, instead of one.

This is the only profile that is also an install-time tier. There is no supported path to it on a
running cluster today — see [changing a profile later](#changing-a-profile-later) — and the
three-node path itself has not yet been installed on real hardware. What each tier does and does
not promise, and what that gap means, is on [HA tiers](/platform/ha).

## Changing a profile later

Not all profiles are equal here, and the differences are not cosmetic — two of them can lose data.

| Profile | Add later | Remove later |
|---|---|---|
| `observability` | Yes | Yes — you lose collected history, nothing else |
| `secrets` | Yes | **No.** Removing it leaves every sealed secret undecryptable |
| `ha` | **No** — not supported today | **No** |

**`observability`** is genuinely reversible. Add it, remove it, add it again. Removing deletes the
metrics and logs it collected; nothing else in the cluster notices.

**`secrets`** is add-only in practice. Adding it is safe. Removing it uninstalls the controller
that holds the sealing key, and every `SealedSecret` in your Git repository becomes permanently
undecryptable. To genuinely stop using it you must first convert every sealed secret back to
another mechanism, and only then remove the profile.

**`ha`** is chosen at install and cannot be changed afterwards today.

Not because the datastore is in the way. Every tier runs embedded etcd — `single-server` runs a
single-node etcd, not SQLite — so moving to `ha` is joining two more servers to an existing etcd
cluster rather than converting a datastore. The installer already performs that join on a fresh
`--ha ha` install. What is missing is the day-2 path: nothing joins servers to a cluster that is
already installed, an install whose tier has changed is refused as a different install rather than
resumed, and it is not something to attempt by hand on a cluster you care about.

So: choose the tier you want at install. Growing into `ha` later is not something the platform
offers today.

**Adding a component profile is an upgrade.** When that path is built it runs through the upgrade
machinery rather than beside it: the same pre-flight gates, the same journal, the same rollback,
the same maintenance window, the same stage reporting to your console. Which gates apply is a
function of what the change actually does — an additive profile install moves no Kubernetes
version, so there is nothing for a deprecated-API scan to find — but the guarantees are the ones
you already have for an upgrade, because there is one code path rather than two that drift.

## Replicated storage is not a profile today

Block storage replicated across nodes was going to be a fourth profile. It is not in Platform 1.x.

No engine had been tested against core, no client had asked for one, and it was the lowest
priority of the four. Carrying a pinned engine nobody had run would have meant the bundle claiming
to have tested something it had not, which is the one claim everything else here rests on. So the
pin came out rather than shipping with a caveat attached to it.

Until it returns, storage durability comes from Local PV LVM in core plus backups that are
restore-tested weekly, and from application-level replication where a workload needs it. A
workload that genuinely cannot tolerate node-local storage needs an external storage system today.
If that is you, say so — a client who needs it is what brings the profile back, with an engine
chosen and tested rather than pinned in advance.

## What gets recorded

The profile set is recorded against your cluster at install and updated on every change:

```
cluster-a: Platform 1.0 + [observability, secrets]
           ha-tier: single-server
           volume-group: customer-created
```

This is not bookkeeping. **The upgrade path depends on it.** Upgrading is
`Platform 1.0 → 1.1 for this exact profile set`, and it is only a tested transition because we
know which set that is. A cluster whose profile record is wrong is a cluster we cannot safely
upgrade — and an unknown profile name is rejected at install rather than quietly ignored, for the
same reason.

The record is also what the fleet view is built on: the control plane holds every cluster's bundle
version, profile set and HA tier, and the installer's last stage compares that record against what
is actually on the cluster before it calls the install done. A cluster whose record and reality
disagree is caught there rather than during an upgrade.
