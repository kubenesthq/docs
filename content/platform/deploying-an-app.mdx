# Deploying an app

Once the platform is installed, the cluster is a standard Kubernetes cluster with a
tested set of components on it. Deploy to it however you already deploy to Kubernetes.

<Callout type="info">
**This page is short on purpose.**

The platform is the product: the pinned core bundle and the cluster lifecycle around it. Nothing
here is a better way to deploy an application than the one you have, and it is not trying to be.
If your team is happy with its current deployment pipeline, keep it — nothing on this page is
required to use KubeNest, and pointing your existing CI at the cluster is a completely supported
way to work.
</Callout>

## Your existing pipeline

The cluster is standard Kubernetes. `kubectl`, `helm`, your own CI, Flux, someone else's ArgoCD —
all work, and none of them need KubeNest to be involved.

The platform gives you a working ingress with Gateway API, TLS through cert-manager, and a default
StorageClass that provisions. Velero is installed too, but it protects workloads only after you
configure a backup target. That applies regardless of how the workload got there.

## Through KubeNest

If you would rather not build the pipeline, KubeNest includes an app layer. Both routes use ArgoCD,
but workload values are not committed to Git. The backend stores the App as a `StackDeploy` and
creates Applications in the control-plane ArgoCD with inline Helm values.

**A Helm chart** — point at a chart and supply values. The backend puts the chart source and values
in an ArgoCD Application, and ArgoCD syncs it.

**Primitives** — describe a workload as components and let KubeNest generate the manifests.

Addon components have a separate operator path: the operator commits their chart and values files
to Git, then creates an ArgoCD Application that points at that directory. A new platform install
does not yet deliver the per-cluster repository credential to that path, so addon components are
not ready there yet.

Both are covered in the existing documentation:

- [Creating apps](/guides/creating-apps)
- [Deploying from a Helm chart](/guides/from-chart)
- [Apps](/concepts/apps) and [stack templates](/concepts/stack-templates) for the underlying model
- [GitOps architecture](/architecture/gitops) for how it reaches the cluster

## What the platform gives your workloads

Worth knowing, because it changes what you need to configure:

| | What you get |
|---|---|
| **Ingress** | Traefik with Gateway API. Write `HTTPRoute`, not `Ingress` |
| **TLS** | cert-manager issues and renews certificates. The install provides a cluster-local default; configure a public or enterprise issuer for customer hostnames |
| **Storage** | A default StorageClass backed by OpenEBS Local PV LVM. PVCs bind without configuration |
| **Backup** | Velero is installed. Protection starts when you configure a target; verified restore drills are not available yet |

Two things to know rather than discover:

**Write `HTTPRoute`, not `Ingress`.** The bundle is Gateway API native. Existing `Ingress`
resources can be converted with `ingress2gateway`; that is a separate migration.

**Local storage is node-local.** A pod using a Local PV LVM volume is bound to the node holding
it, and if that node is lost the volume is gone — restore it from backup. Workloads needing
storage that survives node loss need a replicated or external storage system. The documented
[`replicated-storage` profile](/platform/profiles#replicated-storage) is not installable yet.
