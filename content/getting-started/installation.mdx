# Installation

This guide installs the KubeNest operator on a Kubernetes cluster that already exists. If you want
KubeNest to build a complete k3s cluster and its platform components on Ubuntu hosts, use
[`kubenest platform install`](/platform/install) instead.

The operator connects outbound to the KubeNest hub, receives desired state, reconciles
`StackDeploy` and `StackTemplate` resources through ArgoCD, and reports status back to the control
plane. No inbound port is required for KubeNest itself.

## What the chart installs

The operator chart is `oci://ghcr.io/kubenesthq/charts/kubenest-operator-2`. Chart version 2.3.5
contains four optional dependencies:

| Component | Default | Toggle |
|---|---:|---|
| ArgoCD | enabled | `bootstrap.argocd.enabled` |
| cert-manager | enabled | `bootstrap.certManager.enabled` |
| Gitea | enabled | `bootstrap.gitea.enabled` |
| Vault | disabled | `bootstrap.vault.enabled` |

The chart does **not** contain an ingress controller. KubeNest platform clusters use Traefik and
Gateway API; ingress-nginx was removed from the chart after reaching end of life.

Disable a dependency when the cluster already runs it. Do not disable ArgoCD unless another ArgoCD
installation is available to reconcile the operator's `Application` resources.

## Prerequisites

- Kubernetes with cluster-admin access for the installation
- Helm 3.8 or newer
- Outbound WSS access from the cluster to the hub URL
- An authenticated control-plane token with the `clusters:register` scope
- `jq` for the API examples below

<Steps>

### Create a cluster record

Create the record under your organization. The response is deliberately credential-free: neither
the agent JWT nor a Git credential is returned to browser-facing cluster APIs.

```bash filename="terminal"
curl -sS -X POST "https://api.your-domain.com/api/v1/orgs/$ORG_ID/clusters" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"prod-cluster","description":"Production Kubernetes cluster"}'
```

The response includes the cluster ID and a CLI pointer:

```json filename="cluster record response"
{
  "id": "a1b2c3d4-0001-0000-0000-000000000000",
  "name": "prod-cluster",
  "status": "pending",
  "cli_command": "kubenest cluster connect --cluster a1b2c3d4-0001-0000-0000-000000000000"
}
```

`cli_command` is the invocation the API intends, not one you can run yet: `kubenest cluster connect`
is not an implemented subcommand — the CLI's `cluster` command currently registers only
`set-window`. Keep following this guide, which uses the Helm path that works today.

Save the ID:

```bash filename="terminal"
CLUSTER_ID="a1b2c3d4-0001-0000-0000-000000000000"
```

### Mint the one-time install credentials

Credentials are issued only by an authenticated `POST`. Calling this endpoint again rotates the
agent JWT and, when configured, the repository deploy key.

```bash filename="terminal"
umask 077
curl -sS -X POST \
  -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/clusters/$CLUSTER_ID/agent-credentials" \
  > agent-credentials.json
```

The response shape is:

```json filename="agent-credentials.json"
{
  "cluster_id": "a1b2c3d4-0001-0000-0000-000000000000",
  "agent_jwt": {
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "expires_at": "2027-08-22T00:00:00Z",
    "hub_url": "wss://hub.your-domain.com/ws/operator",
    "token_version": 1
  },
  "repo_credential": {
    "type": "ssh_deploy_key",
    "private_key": "-----BEGIN OPENSSH PRIVATE KEY-----\n...\n-----END OPENSSH PRIVATE KEY-----",
    "repo_url": "ssh://git@git.your-domain.com/kubenest/gitops-a1b2c3d4.git",
    "branch": "main"
  },
  "operator": {
    "namespace": "kubenest-system",
    "chart_ref": "oci://ghcr.io/kubenesthq/charts/kubenest-operator-2:2.3.5"
  }
}
```

`repo_credential` is `null` when the control plane has no GitOps broker configured. In that mode,
leave the bundled Gitea enabled instead of setting `bootstrap.gitea.enabled: false`.

### Prepare the Helm values

Create `kubenest-operator-values.yaml` with mode `0600`. Map `agent_jwt.hub_url` to the chart's
`kubenest.backendURL` key. The name is historical; the value is the operator WebSocket endpoint.

```yaml filename="kubenest-operator-values.yaml"
kubenest:
  backendURL: wss://hub.your-domain.com/ws/operator
  jwtSecret: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
  clusterID: a1b2c3d4-0001-0000-0000-000000000000

  bootstrapController:
    gitRepoURL: ssh://git@git.your-domain.com/kubenest/gitops-a1b2c3d4.git
    gitRepoBranch: main
    gitSSHPrivateKey: |
      -----BEGIN OPENSSH PRIVATE KEY-----
      ...
      -----END OPENSSH PRIVATE KEY-----

bootstrap:
  argocd:
    enabled: true
  certManager:
    enabled: true
  gitea:
    enabled: false
  vault:
    enabled: false
```

```bash filename="terminal"
chmod 600 kubenest-operator-values.yaml
```

The chart renders `kubenest.clusterID` and `kubenest.jwtSecret` into the
`kubenest-operator-token` Secret. The Deployment reads both identity values from that Secret with
non-optional references, so a missing Secret is a visible `CreateContainerConfigError`, not a
healthy-looking operator with an empty cluster ID.

The credential response does not yet include the Git server's SSH host key. Until that contract is
extended, the operator and ArgoCD accept the repository host without verification and log the
degraded posture. Do not invent a `gitSSHKnownHosts` value; obtain the real host key out of band or
leave it empty. Host-key delivery is tracked by `kn-rnyl.1`.

### Render before installing

Render the exact values file before changing the cluster:

```bash filename="terminal"
helm template operator oci://ghcr.io/kubenesthq/charts/kubenest-operator-2 \
  --version 2.3.5 \
  --namespace kubenest-system \
  --values kubenest-operator-values.yaml \
  > /tmp/kubenest-operator-rendered.yaml
```

Confirm that the rendered Deployment contains the requested URL and that the identity Secret has
both keys:

```bash filename="terminal"
grep -A1 KUBENEST_BACKEND_URL /tmp/kubenest-operator-rendered.yaml
grep -E 'cluster-id:|token:' /tmp/kubenest-operator-rendered.yaml
```

### Install the operator

Use the short release name `operator`. Longer names can push chart-generated Kubernetes resource
names past the 63-character limit.

```bash filename="terminal"
helm upgrade --install operator oci://ghcr.io/kubenesthq/charts/kubenest-operator-2 \
  --version 2.3.5 \
  --namespace kubenest-system \
  --create-namespace \
  --values kubenest-operator-values.yaml \
  --wait
```

Delete the local credential files after Helm has accepted the release:

```bash filename="terminal"
rm agent-credentials.json kubenest-operator-values.yaml
```

### Verify the connection

```bash filename="terminal"
kubectl get deployment operator-kubenest-operator-2-controller-manager \
  -n kubenest-system

kubectl logs -n kubenest-system \
  -l app.kubernetes.io/instance=operator \
  --tail=30
```

Look for `WebSocket connection established`, then confirm the control-plane record reports
`connected`:

```bash filename="terminal"
curl -sS -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/clusters/$CLUSTER_ID" | jq -r .status
```

</Steps>

## Key Helm values

| Value | Required | Default | Purpose |
|---|---:|---|---|
| `kubenest.backendURL` | Yes for self-hosting | `wss://api.kubenest.io/v2/operator/events` | Hub WebSocket endpoint |
| `kubenest.jwtSecret` | Yes in values mode | `""` | Agent JWT; rendered into the identity Secret |
| `kubenest.clusterID` | Yes in values mode | `""` | Cluster UUID; rendered into the identity Secret |
| `kubenest.operatorTokenSecret` | No | `kubenest-operator-token` | Existing identity Secret name for externally managed credentials |
| `kubenest.bootstrapController.gitRepoURL` | Conditional | `""` | Per-cluster GitOps repository |
| `kubenest.bootstrapController.gitRepoBranch` | No | `main` | GitOps branch |
| `kubenest.bootstrapController.gitSSHPrivateKey` | Conditional | `""` | Per-repository write deploy key |
| `kubenest.bootstrapController.gitSSHKnownHosts` | Recommended when known | `""` | SSH host-key pin; not yet returned by the credential API |
| `kubenest.bootstrapController.gitCredentialSecret` | No | chart-created Secret | Existing SSH credential Secret name |
| `bootstrap.argocd.enabled` | No | `true` | Install bundled ArgoCD |
| `bootstrap.certManager.enabled` | No | `true` | Install bundled cert-manager |
| `bootstrap.gitea.enabled` | No | `true` | Install bundled single-cluster Gitea |
| `bootstrap.vault.enabled` | No | `false` | Install bundled Vault |

## Rotating install credentials

`POST /clusters/{id}/agent-credentials` is a rotation operation, not a read. It increments the JWT
token version and replaces the per-cluster deploy key. After calling it, update both credentials in
the Helm values and run the same `helm upgrade --install` command.

The hub currently validates JWT signature and claims but does not yet enforce `token_version`.
Therefore an older JWT remains valid until it expires; full revocation is tracked separately.

## Troubleshooting

**The pod is in `CreateContainerConfigError`.** Check that the rendered
`kubenest-operator-token` Secret contains both `token` and `cluster-id`, or that the Secret named by
`kubenest.operatorTokenSecret` exists.

**The cluster stays `pending`.** Verify the rendered `KUBENEST_BACKEND_URL`, DNS and outbound WSS
connectivity from the cluster. For production, the URL should use `wss://` and include the operator
WebSocket path.

**ArgoCD Applications are not created.** If `bootstrap.argocd.enabled` is false, confirm an
existing ArgoCD installation is healthy and watches the operator's `Application` resources.
