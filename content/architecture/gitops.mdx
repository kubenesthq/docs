# GitOps and Drift Detection

kubenest uses ArgoCD for both workload and addon reconciliation, but the two paths are different.
Workloads do not produce Git commits: the backend stores the App as a `StackDeploy` and creates an
`Application` in the control-plane ArgoCD for each workload component, with Helm values inline.
Addons use Git: the addon controller commits their chart and values files, then creates an
`Application` in the tenant cluster that points at that directory.

## Where Git is used

ArgoCD is the common reconciliation layer. Git is the source for addons, but not for workloads.

**Workload history is outside Git.** App operations are recorded as `Deployment` rows in
PostgreSQL. Mutations that support rollback store a prior `StackDeploy` snapshot there. A Git log
is not a complete audit trail for workload deploys, patches, redeploys, or rollbacks.

**Addon history is in Git.** Each addon reconciliation writes `Chart.yaml` and `values.yaml` under
the cluster's addon directory and commits the change. These commits do not include workload state.

**ArgoCD still detects live drift.** Workload Applications use inline Helm values; addon
Applications use files in Git. Both enable automated sync, pruning, and self-healing against their
respective desired state.

**The object model is the workload record.** For workloads, inspect the `StackDeploy`, its child
`Workload` objects, and the ArgoCD `Application` specs. The Git repository alone cannot reconstruct
the workload configuration.

## How a workload reaches Kubernetes

The path from `POST /api/v1/apps` to running pods uses the following objects.

<Steps>

### App and StackDeploy creation

The App API is a wrapper around a `StackDeploy` custom resource. On create, the backend writes that
resource to the project's cluster and records a `Deployment` row. The `StackDeploy` spec contains
the component list, dependency information, and timeout.

### Component expansion

The operator's StackDeploy controller expands local components into child custom resources in
dependency order:

- A workload component becomes a `Workload`.
- An addon component becomes an `Addon`.

The controller resolves `exportRef` values between those child objects and aggregates their status
back onto the `StackDeploy`.

### Workload Application upsert

The backend creates or updates one ArgoCD `Application` for each workload component. For a
KubeNest primitive it uses the KubeNest workload chart; for chart mode it uses the supplied chart.
In both cases, the Helm values are stored inline in the `Application` spec rather than committed to
Git. The Application targets the component's cluster and namespace.

```yaml
spec:
  source:
    repoURL: https://kubenesthq.github.io/charts
    chart: kubenest-workload
    targetRevision: <chart-version>
    helm:
      releaseName: {component-name}
      values: <inline Helm values>
  destination:
    name: {cluster-name}
    namespace: {namespace}
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

This workload path creates no Git commit.

### Addon Git commit

For an addon component, the Addon controller writes `Chart.yaml` and `values.yaml` under
`clusters/{cluster-id}/addons/{namespace}-{addon-name}`, commits them, and creates or updates an
ArgoCD `Application` that points at that path. This is a separate flow from workload rendering.

### ArgoCD sync and status emission

ArgoCD syncs each Application and updates its health and sync status. For workloads, the backend
watches the control-plane ArgoCD Applications and relays their status through the hub to the tenant
operator. The Workload controller combines that status with locally observed resources, and the
StackDeploy controller aggregates the child states. The API reads the resulting StackDeploy status.

</Steps>

## The addon GitOps repository layout

The addon controller writes this structure:

```
gitops-repo/
└── clusters/
    └── {cluster-id}/
        └── addons/
            └── {namespace}-{addon-name}/
                ├── Chart.yaml
                └── values.yaml
```

The directory contains the addon's chart dependency and Helm values. Workload components do not
appear in this tree. A `git diff` shows addon changes only; use the App API or inspect the
`StackDeploy` and workload ArgoCD Applications for workload state.

## Drift detection

Drift occurs when live Kubernetes resources diverge from their desired state. For workloads, that
state comes from the Workload and the ArgoCD Application's inline Helm values. For addons, it comes
from the addon directory in Git.

### How drift is detected

ArgoCD reports Application sync and health. The Workload controller also compares the desired image
and replica count with the observed Deployment. It records those details on the Workload status,
and the StackDeploy controller aggregates child sync state.

The API exposes this as the `sync` block on the App response:

```json
{
  "name": "my-app",
  "phase": "Running",
  "sync": {
    "driftDetected": true,
    "driftClass": "recoverable",
    "driftDetails": [
      {
        "resource": "Deployment/my-app-web",
        "field": "spec.replicas",
        "desired": 2,
        "observed": 1
      }
    ]
  }
}
```

### Drift classes

kubenest categorizes drift into two classes based on the impact on subsequent operations.

**`recoverable`** — the recorded differences do not contain a blocked item. ArgoCD Applications
have self-healing enabled, so ArgoCD can re-apply their desired resources.

**`blocked_sync`** — at least one detail is blocked. The operator marks ArgoCD `Unknown` or `Error`
sync state, or `Degraded` health, as blocked. App mutation routes that apply the drift guard return
`409 Conflict` until the Application or cluster condition is resolved.

<Callout type="warning">
Treat workload ArgoCD Applications and addon Git directories as KubeNest-managed desired state.
Direct edits can be overwritten by the next API operation or controller reconciliation.
</Callout>

## Triggering a redeploy

A redeploy asks ArgoCD to hard-refresh each workload Application without changing the spec. This
makes ArgoCD re-read the chart and live resources. It does not guarantee a pod restart when the
desired state is unchanged.

```bash
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  https://api.your-domain.com/api/v1/apps/my-project/my-app/redeploy
```

Under the hood, the backend requests a hard refresh on each workload component's ArgoCD
Application. It does not change the StackDeploy spec and does not create a Git commit.

The redeploy is recorded as a new Deployment row in the history, so you can distinguish a forced redeploy from a natural pod restart.

## Rollback mechanics

KubeNest records app operations in PostgreSQL `Deployment` rows. Mutations that support rollback
store a `prior_state` snapshot of the StackDeploy. A rollback target must contain that snapshot.

Rolling back to a prior deployment replays that snapshot through the same reconcile path:

<Steps>

### Identify the target revision

List the deployment history to find the revision you want:

```bash
curl -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/apps/my-project/my-app/deployments" | jq '.[] | {id, created_at, phase, message}'
```

### Trigger the rollback

```bash
curl -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"deployment_id": "d4e5f6g7-..."}' \
  https://api.your-domain.com/api/v1/apps/my-project/my-app/rollback
```

### What happens

The backend restores the `prior_state` spec from the target Deployment row. It then:

1. Patches the StackDeploy with the restored component list and timeout.
2. Rebuilds and upserts the inline-value ArgoCD Applications for restored workload components.
3. Deletes workload Applications for components absent from the restored snapshot.
4. Records the rollback as another Deployment row.

The operator reconciles the changed StackDeploy and its child objects. If the restored spec changes
an addon, that addon's normal controller flow can produce an addon Git commit.

</Steps>

The rollback is a forward application of an older StackDeploy configuration, not a Git revert or a
Helm rollback. Workload rollback history is in the Deployment records, not the Git repository.

ArgoCD then reconciles the restored chart and values. A restored image or chart reference must
still be available for that reconciliation to succeed.

<Callout type="info">
Addon components within an App are **included** in the rollback snapshot. If the prior spec had a different chart version for a PostgreSQL addon, rolling back will trigger a Helm downgrade of that chart. Consider the data implications before rolling back an App that contains stateful addons — Helm addon downgrades can be schema-incompatible.
</Callout>
