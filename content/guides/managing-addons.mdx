# Managing Addons

An addon is a Helm chart-based backing service: a database, a cache, a message broker, a search engine. In kubenest, addons can be deployed in two ways: as a component inside an App (tightly coupled to the App's lifecycle), or as a standalone `AddonInstance` (independently managed, shareable across multiple Apps). This guide focuses on standalone addon instances.

If you want to bundle an addon with an App, see the [Creating and Managing Apps](/guides/creating-apps) guide and the [Addons](/concepts/addons) concept page.

---

## What addon instances are

A standalone `AddonInstance` is a Helm chart deployment with its own lifecycle: it is created, upgraded, and deleted independently of any App. It lives in a project namespace and exposes **exports** — key-value outputs like connection strings, passwords, and hostnames — that workload components in the same project can consume via `exportRef`.

The canonical use case is a shared database: one PostgreSQL instance that two or three Apps in the same project all connect to. Managing it as a standalone instance means you can upgrade the chart, rotate credentials, or adjust resource limits without touching any of the Apps that depend on it.

## Available addon types

The `AddonDefinition` catalog lists the officially supported addon types. Browse it:

```bash filename="list addon definitions"
curl -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/addon-definitions" | jq '.data[] | {name, chart_name, chart_version}'
```

Commonly available types:

| Addon type | Chart | Export keys |
|---|---|---|
| `postgres` | `bitnami/postgresql` | `dsn`, `host`, `port`, `user`, `database`, `sslMode`, `passwordRef.name`, `passwordRef.key` — plus the aliases `DATABASE_URL`, `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE` |
| `redis` | `bitnami/redis` | `host`, `port`, `database`, `passwordRef.name`, `passwordRef.key` |
| `kafka` | `bitnami/kafka` | `bootstrapServers`, `saslSecretRef.name`, `saslSecretRef.usernameKey`, `saslSecretRef.passwordKey` |
| `mongodb`, `mysql`, `rabbitmq` | (any chart) | No type-specific extractor. They fall through to the generic one below |
| `custom` | (any chart) | `service.url`, `service.port`, and `ingress.url` where an Ingress exists |

The type is the addon's `type` field, not its chart name — `postgres` deploys the chart named
`postgresql`, which is where most of the confusion comes from. A type outside this list, or a
misspelling like `postgresql`, is rejected by the API rather than silently deployed.

**A password is never an export value.** For the types that have one, the addon publishes a
`passwordRef` naming the Kubernetes Secret and key it lives in, and you read it from the cluster.
Nothing in the control plane will hand you the password itself.

<Callout type="warning">
The `postgres` `dsn` export currently contains a literal `${postgres-password}` where the password
belongs, and nothing substitutes it — so a workload wiring its connection string from `dsn` gets a
credential it cannot use. Tracked as `kn-kgu5`. Until that lands, read the password from the Secret
named by `passwordRef` and assemble the connection string yourself.
</Callout>

## Deploying a standalone addon

Create an addon instance by posting to `/api/v1/addon-instances`. You must supply the project the instance belongs to and either a `definition_id` (referencing a catalog entry) or a `type` + `chart` directly.

<Tabs items={['Using a definition', 'Custom chart (no definition)']}>
<Tabs.Tab>

```bash filename="create addon instance from definition"
# Get the definition ID first
DEFINITION_ID=$(curl -s -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/addon-definitions" | \
  jq -r '.data[] | select(.slug=="postgres") | .id')

curl -X POST https://api.your-domain.com/api/v1/addon-instances \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "my-postgres",
    "project_id": "b2c3d4e5-0002-0000-0000-000000000000",
    "definition_id": "'"$DEFINITION_ID"'",
    "values": {
      "auth": {
        "database": "myapp",
        "username": "myapp",
        "password": "mysecretpassword"
      },
      "primary": {
        "persistence": {
          "size": "10Gi"
        }
      }
    }
  }'
```

When a `definition_id` is provided, the backend merges your `values` on top of the definition's default values. The chart reference (repo, name, version) comes from the definition — you do not need to specify it.

</Tabs.Tab>
<Tabs.Tab>

```bash filename="create addon instance without definition"
curl -X POST https://api.your-domain.com/api/v1/addon-instances \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "my-custom-addon",
    "project_id": "b2c3d4e5-0002-0000-0000-000000000000",
    "type": "custom",
    "chart": {
      "repo": "https://charts.example.com",
      "name": "my-custom-chart",
      "version": "2.1.0"
    },
    "values": {
      "replicaCount": 1
    }
  }'
```

Without a definition, kubenest cannot auto-discover exports. You will need to read export values directly from the cluster Secret if you need them.

</Tabs.Tab>
</Tabs>

The response includes the addon instance `id` and initial `phase: Pending`. The operator deploys the Helm chart asynchronously.

## Watching deploy progress

```bash filename="watch addon deploy"
INSTANCE_ID="instance-uuid-..."

curl -N -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/events/stream?cluster_id=$CLUSTER_ID&resource_type=addon"
```

The phase sequence for a healthy deploy:

```
Pending → Deploying → Running
```

`Deploying` can take several minutes for large charts (PostgreSQL with persistence, Kafka with Zookeeper). The operator polls the ArgoCD Application health status and emits a status event each time it changes.

## Reading exports

After the addon reaches `Running`, its exports are available on the instance record:

```bash filename="read exports"
curl -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/addon-instances/$INSTANCE_ID" | jq .exports
```

Example output for a PostgreSQL instance:

```json
{
  "dsn": "[stored in K8s Secret]",
  "host": "[stored in K8s Secret]",
  "port": "[stored in K8s Secret]",
  "user": "[stored in K8s Secret]",
  "database": "[stored in K8s Secret]"
}
```

For a secret-backed addon the API returns the export **keys**, not the values. Every value reads
`[stored in K8s Secret]`. The full response also carries `exports_mode: "secret"` and a
`secret_ref` naming the Kubernetes Secret and namespace the values actually live in.

<Callout type="warning">
The API never returns export values. To read them you go to the cluster — `kubectl get secret` in
the addon's namespace, using the name in `secret_ref`. Nothing in the control plane will hand you
a password.

This also means the API response is not a way to check what a value *is*. Components inside an App
do not need it: `exportRef` wiring is resolved by the operator inside the cluster, so a workload
receives the real value in its environment without the value ever passing through the backend.
</Callout>

## Upgrading an addon

Update an addon's Helm values with a PATCH request. Common reasons to patch: increasing storage size, changing resource requests, enabling a replica set, or rotating a password.

The body takes **exactly one** of `values` or `chart_version` — never both, and never neither. Sending both is rejected. Change the values in one request and the chart version in another.

```bash filename="upgrade addon values"
curl -X PATCH https://api.your-domain.com/api/v1/addon-instances/$INSTANCE_ID \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "values": {
      "primary": {
        "resources": {
          "requests": {
            "memory": "512Mi",
            "cpu": "250m"
          },
          "limits": {
            "memory": "1Gi",
            "cpu": "500m"
          }
        }
      }
    },
    "note": "Increase memory for production load"
  }'
```

The `note` field is stored on the revision record and appears in the revision history. Use it to leave a human-readable explanation of why the change was made — your future self will thank you.

The PATCH creates a new **revision** and triggers a `helm upgrade`. The operator emits status events throughout the upgrade. If the upgrade fails, the revision is marked `Failed` and the previous revision's values remain active (Helm's rollback-on-failure behavior).

To upgrade the chart version itself:

```bash filename="upgrade chart version"
curl -X PATCH https://api.your-domain.com/api/v1/addon-instances/$INSTANCE_ID \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "chart_version": "16.5.0",
    "note": "Upgrade postgresql chart to 16.5.0"
  }'
```

## Revision history and rollback

Every PATCH to an addon instance creates a revision. List the full history:

```bash filename="list revisions"
curl -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/addon-instances/$INSTANCE_ID/revisions" | \
  jq '.[] | {revision_number, created_at, phase, note}'
```

Example output:

```json
[
  { "revision_number": 3, "created_at": "2026-06-11T15:22:00Z", "phase": "success", "note": "Increase memory for production load" },
  { "revision_number": 2, "created_at": "2026-06-10T09:41:00Z", "phase": "success", "note": "Enable connection pooling" },
  { "revision_number": 1, "created_at": "2026-06-08T14:00:00Z", "phase": "success", "note": "Initial deploy" }
]
```

Roll back to a prior revision:

```bash filename="rollback by revision number"
curl -X POST https://api.your-domain.com/api/v1/addon-instances/$INSTANCE_ID/rollback \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "revision_number": 1,
    "note": "Reverting memory increase — caused OOMKill on nodes"
  }'
```

You can also roll back by `revision_id` (UUID) if you have it from a previous API call. The rollback creates a **new revision** (revision 4 in this example) with the values from the target revision — the history remains intact and linear.

<Callout type="warning">
Rolling back an addon's chart version can involve a Helm downgrade. Helm supports this mechanically, but many database charts are not designed for version downgrades — they may run schema migrations on upgrade that cannot be reversed. Always snapshot the database before rolling back a stateful addon to a prior chart version.
</Callout>

## Attaching a standalone addon to an App

To wire a standalone addon instance's exports into a workload component that belongs to an existing App, reference the instance by ID in the component's `exportRef`:

```bash filename="patch app to wire standalone addon"
INSTANCE_ID="c3d4e5f6-..."

curl -X PATCH "https://api.your-domain.com/api/v1/apps/my-project/my-app?project_id=$PROJECT_ID" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "components": [
      {
        "name": "api",
        "type": "workload",
        "workload_spec": {
          "build_mode": "image",
          "image": "myorg/my-api:v1.0.0",
          "replicas": 2,
          "port": 8000,
          "env": [
            {
              "name": "PGHOST",
              "export_ref": {
                "addon_instance_id": "'"$INSTANCE_ID"'",
                "export_key": "host"
              }
            }
          ]
        }
      }
    ]
  }'
```

A `components` entry replaces that component wholesale rather than merging, so send its complete spec — see [Creating apps](/guides/creating-apps#updating-an-app). This PATCH triggers a full reconcile of the `api` component: the operator re-renders its Helm values with the resolved export and pushes a rolling update. The standalone addon instance is not modified.

The example wires `host` rather than the `dsn` connection URL deliberately: `dsn` carries an unsubstituted `${postgres-password}` placeholder today (`kn-kgu5`), so it is not a usable connection string. See [Addons](/concepts/addons#exports-how-addons-publish-their-outputs).

You can wire the same addon instance into multiple Apps simultaneously. The addon is unaware of how many workloads depend on it.

## Deleting an addon instance

```bash filename="delete addon instance"
curl -X DELETE https://api.your-domain.com/api/v1/addon-instances/$INSTANCE_ID \
  -H "Authorization: Bearer $TOKEN"
```

Be clear about what this does before running it. The delete sends an `addon_uninstall` event toward the cluster and then removes the instance record from the control plane. If the hub is not reachable when you call it, the delete fails with `502` and the record is kept — the control plane will not drop its record while the cluster cannot be told to uninstall.

On the cluster, the event deletes the Addon resource and nothing else. The ArgoCD Application that actually deploys the chart is linked to the Addon by label, not ownership, and is not removed — so the Helm release, its workloads, and its PersistentVolumeClaims keep running after the delete.

There is no flag that changes this. The delete accepts no parameters — in particular, there is no `preserve_pvcs` option, because the delete does not remove data in the first place.

Cleaning up the cluster is manual:

```bash filename="manual cleanup on the cluster"
# The ArgoCD Application is named <project-namespace>-addon-<instance-name>,
# lives in kubenest-system, and is labelled with the addon's name. It carries
# ArgoCD's resources finalizer, so deleting it removes the chart's resources.
kubectl get applications -n kubenest-system -l kubenest.io/addon-name=my-postgres
kubectl delete application my-project-addon-my-postgres -n kubenest-system

# PVCs created by a StatefulSet's volumeClaimTemplates are not part of the
# rendered chart and survive the Application delete. List them and delete
# explicitly if the data should go:
kubectl get pvc -n my-project
```

If the uninstall event never reached the cluster — a narrow edge case where the connection dropped while the delete was in flight — the Addon resource is still there too:

```bash filename="if the cluster was disconnected"
kubectl delete addon my-postgres -n my-project
```

<Callout type="warning">
**Check dependent workloads before deleting.** There is no API that lists an addon's dependents. Before deleting a shared addon, check each App in the project for workload environment variables whose `export_ref` points at this instance — once the instance record is gone, that wiring has nothing to resolve against.
</Callout>

## Common pitfalls

**Export keys vary for custom (definition-less) addons.** The standard export keys (`dsn`, `host`, `port`, etc.) come from the operator's per-type extractor and are mirrored in the `AddonDefinition`'s export schema. For a `custom` type addon without a definition, kubenest cannot auto-discover exports — they will be empty. You must read the relevant values from the Kubernetes Secret the chart creates and set them manually as workload environment variables, or create a custom `AddonDefinition` that specifies the export schema.

**`Deploying` phase that never transitions to `Running`.** The most common cause is the chart's readiness probe never passing — typically because a password is too long (some chart versions have PostgreSQL password length limits), the PVC cannot be provisioned (storage class unavailable), or the image pull is failing. Check the ArgoCD Application in the cluster for the detailed Helm release status.

**Upgrading to a chart version that drops a values key you are using.** If a chart upgrade removes a values key your `values` payload specifies, Helm will typically ignore the extra key — but the behavior is chart-specific. Always read the chart's changelog before upgrading a minor or major version.
