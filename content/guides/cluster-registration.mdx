# Registering a Cluster

A cluster must be registered with kubenest before you can deploy applications to it. Registration is always a two-part process: creating a cluster record in the backend (which issues a cluster JWT), and installing the operator on the actual Kubernetes cluster (which uses that JWT to authenticate with the hub). How the Kubernetes cluster itself comes to exist is what separates the two registration paths.

---

## Path 1: Manual registration (BYO cluster)

Bring-your-own-cluster (BYOC) registration is for clusters that already exist — whether that is a managed service (EKS, GKE, AKE), a self-managed kubeadm cluster, or a local k3s instance. kubenest does not need access to the cloud provider; you install the operator on the cluster yourself.

<Steps>

### Create the cluster record

Cluster records are created under an organization, so you need your organization's UUID. Fetch it from `GET /api/v1/orgs` if you do not already have it:

```bash filename="find your org ID"
ORG_ID=$(curl -s -H "Authorization: Bearer $TOKEN" \
  https://api.your-domain.com/api/v1/orgs | jq -r '.[0].id')
```

Now create the cluster record. This reserves a UUID, mints the cluster JWT, and generates the Helm install command.

For a BYO cluster, **omit** `provider` and `credential_id` entirely — their presence is what tells kubenest to provision infrastructure for you. The request body rejects unknown fields, so do not send `"provider": "manual"`; there is no such provider.

```bash filename="create cluster record"
curl -X POST "https://api.your-domain.com/api/v1/orgs/$ORG_ID/clusters" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "prod-cluster",
    "description": "AWS EKS us-east-1 production cluster"
  }'
```

Response (`201 Created`):

```json filename="cluster record response"
{
  "id": "a1b2c3d4-0001-0000-0000-000000000000",
  "name": "prod-cluster",
  "status": "pending",
  "connection_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "install_command": "helm install kubenest-operator oci://registry.kubenest.io/kubenest-operator --namespace kubenest-system --create-namespace --set kubenest.hubURL=wss://hub.your-domain.com/ws/operator --set kubenest.jwtSecret=eyJhbGc... --set kubenest.clusterID=a1b2c3d4-..."
}
```

<Callout type="warning">
**Do not run `install_command` as-is.** The generated command sets `kubenest.hubURL`, a key the operator chart does not read — the chart reads `kubenest.backendURL` — and it pulls from a chart registry that does not currently exist. Run unmodified, the install either fails at the pull or brings up an operator pointed at the chart's default endpoint instead of your hub. Use the `connection_token` and cluster ID with the values file below instead. The [Installation](/getting-started/installation) page has the full explanation.
</Callout>

A manually registered cluster starts in `pending` and moves to `connected` once the operator's WebSocket handshake reaches the hub. Cloud-provisioned clusters start in `provisioning` instead.

Save the cluster ID. You will need it in subsequent API calls:

```bash filename="save cluster ID"
CLUSTER_ID="a1b2c3d4-0001-0000-0000-000000000000"
```

You can also retrieve the install command at any time via the API:

```bash filename="retrieve install command"
curl -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/clusters/$CLUSTER_ID/install-command"
```

Note that this endpoint mints a **new** 365-day cluster JWT on every call and stores it as the cluster's current token. If the operator is already running with an older token, it keeps working (see the note on revocation below), but the command you get back will not match the token in the running Secret. To read the install steps without minting a new token, use `/install-instructions` instead, which reuses the stored token when one exists.

### Prepare your Helm values

For production installs, use a values file rather than a `--set` chain. This makes the configuration auditable and easier to update:

```yaml filename="kubenest-operator-values.yaml"
kubenest:
  # The hub's operator WebSocket endpoint, including the /ws/operator path.
  # The key is named backendURL, but the value is the hub URL.
  backendURL: wss://hub.your-domain.com/ws/operator

  # connection_token from the cluster record. Required.
  jwtSecret: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

  # UUID of the cluster record. Required.
  clusterID: a1b2c3d4-0001-0000-0000-000000000000

  # GitOps repository the operator writes manifests to.
  # Leave gitRepoURL empty to use the chart's bundled Gitea instead.
  bootstrapController:
    gitRepoURL: https://github.com/your-org/gitops-repo
    gitRepoBranch: main
    gitToken: ghp_...   # personal access token with repo:write scope

# Bundled dependencies — ArgoCD, cert-manager, ingress-nginx and Gitea all
# install by default. Disable whatever the cluster already runs.
bootstrap:
  argocd:
    enabled: false      # this cluster already runs ArgoCD
  certManager:
    enabled: false
  ingressNginx:
    enabled: false
  gitea:
    enabled: false      # using the external Git repo above
  vault:
    enabled: false
```

The chart does not validate these values: an install with missing or misspelled keys deploys without complaint and the operator silently dials the chart's default endpoint with an empty token. The [Installation](/getting-started/installation) page covers the failure mode and the full values reference.

The `kubenest.bootstrapController.gitRepoURL` must be a repository that:
- The operator has read/write access to via the provided token.
- Is **not** shared with other clusters unless you understand that they will write to different subtrees (see [GitOps and Drift Detection](/architecture/gitops)).

### Install the operator on the cluster

Make sure `kubectl` is pointing at the target cluster, then install:

```bash filename="install operator"
helm install kubenest-operator oci://ghcr.io/kubenesthq/charts/kubenest-operator-2 \
  --version 2.1.0 \
  --namespace kubenest-system \
  --create-namespace \
  --values kubenest-operator-values.yaml
```

Watch the pod start:

```bash filename="watch pod startup"
kubectl get pods -n kubenest-system -w
```

Expected output once healthy (the resource names include the chart name, `kubenest-operator-2`):

```
NAME                                                            READY   STATUS    RESTARTS   AGE
kubenest-operator-kubenest-operator-2-controller-manager-xyz   1/1     Running   0          30s
```

Check the operator log for the hub connection message:

```bash filename="check operator logs"
kubectl logs -n kubenest-system \
  -l app.kubernetes.io/instance=kubenest-operator \
  --tail=30
```

Look for:

```
WebSocket connection established
```

### Confirm the cluster is connected

Once the operator connects, the hub notifies the backend, which transitions the cluster status from `pending` to `connected`:

```bash filename="verify cluster status"
curl -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/clusters/$CLUSTER_ID" | jq .status
# "connected"
```

The cluster is now ready to receive deployments. Create a project and deploy your first app — see [Creating and Managing Apps](/guides/creating-apps).

</Steps>

<Callout type="warning">
**Secure the cluster JWT.** The connection token is a long-lived credential with the ability to execute any operation the operator supports on that cluster. The Helm chart does **not** put it in a Kubernetes Secret: `kubenest.jwtSecret` is rendered into the operator Deployment as a plain environment variable, readable by anyone who can read Deployments in the namespace. The chart does read an optional Secret named `kubenest-operator-token` (keys `token` and `cluster-id`) — if you create one, the operator prefers its token over the rendered value, and you can then keep the token out of your values file entirely.

Create that Secret regardless of how you handle the token, because `kubenest.clusterID` is accepted by the chart and never used — it is not rendered into the Deployment, and `CLUSTER_ID` comes only from the Secret's `cluster-id` key. Without the Secret the operator runs with an empty cluster ID while looking healthy. Chart defect, tracked as `kn-lx5t`; see [Installing the operator](/getting-started/installation) for the exact command.

Issuing a new token does **not** revoke the old one. The hub accepts any correctly signed, unexpired cluster JWT — it does not check the token against the one currently stored for the cluster. A leaked token therefore stays usable for the remainder of its 365-day lifetime. If a token is compromised, treat rotating the hub's `JWT_SECRET` (which invalidates every cluster token at once and requires re-issuing all of them) or deleting and re-registering the cluster as the only reliable containment.

To issue a fresh cluster JWT, call `GET /api/v1/clusters/{id}/install-command`. Every call mints a new 365-day token and stores it as the cluster's current token. To roll the operator onto it, set the new token as `kubenest.jwtSecret` in your values file and run `helm upgrade` — or, if you created a `kubenest-operator-token` Secret, update its `token` key and restart the operator pod.
</Callout>

## Path 2: Cloud-provisioned clusters (AWS EC2)

kubenest can provision a Kubernetes cluster on AWS by creating EC2 instances and bootstrapping Kubernetes automatically. This path is appropriate when you do not have an existing cluster and want kubenest to manage the infrastructure lifecycle as well as the application lifecycle.

<Callout type="info">
Cloud-provisioned clusters are supported on **AWS EC2** only. The provisioner uses Terraform under the hood; you need a `CloudCredential` record with valid AWS credentials before proceeding.
</Callout>

### Prerequisites

1. Create a `CloudCredential` record with your AWS credentials:

Credential fields are flat, not nested — the payload rejects unknown fields.

```bash filename="create cloud credential"
curl -X POST "https://api.your-domain.com/api/v1/orgs/$ORG_ID/credentials" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "aws-prod",
    "provider": "aws",
    "region": "us-east-1",
    "access_key_id": "AKIAIOSFODNN7EXAMPLE",
    "secret_access_key": "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
  }'
```

2. The credential ID from the response is used in the cluster create request.

<Callout type="info">
`provider` accepts `aws`, `gcp`, `azure`, `do`, `metal`, and `ssh`. Credentials are accepted for all of them, but **only `aws` is wired for provisioning today** — the others return `422` with a "coming soon" message when you try to create a cluster with them.
</Callout>

### Create a provisioned cluster

Provisioning options are flat fields on the cluster body, not a nested `provision_config`. Setting both `provider` and `credential_id` is what switches this from a BYO registration to a provisioning request.

```bash filename="create cloud cluster"
curl -X POST "https://api.your-domain.com/api/v1/orgs/$ORG_ID/clusters" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "staging-aws",
    "provider": "aws",
    "credential_id": "cred-uuid-...",
    "region": "us-east-1",
    "instance_type": "t3.medium",
    "agent_count": 3,
    "disk_size_gb": 40
  }'
```

`agent_count` is the number of agent nodes (0–20) alongside the control-plane node, and `disk_size_gb` accepts 10–500. If you omit `region`, the credential's own region is used. The Kubernetes version is not selectable — provisioned clusters run the k3s version baked into the provisioner image.

### Status transitions

Cloud-provisioned clusters move through more states than BYOC registrations:

```
pending
  │
  ▼
provisioning          ← Terraform creates VPC, security groups, EC2 instances
  │
  ▼
awaiting_operator     ← VMs are up; k3s is bootstrapped; waiting for operator first connect
  │
  ▼
connected             ← Operator has authenticated; cluster is ready
```

Poll or stream status:

```bash filename="watch provisioning"
curl -N -H "Authorization: Bearer $TOKEN" \
  "https://api.your-domain.com/api/v1/events/stream?cluster_id=$CLUSTER_ID"
```

Provisioning typically takes 5–10 minutes depending on the region and instance count.

### SSH access

The provisioner generates an SSH key pair for the nodes during provisioning. **The private key is not retrievable through the API** — no endpoint serves it. It exists in one place: the Terraform state for the cluster, which the control plane stores in its own PostgreSQL database (schema `terraform_state`, table `states`, one row per cluster, named by the cluster ID).

Retrieving it therefore requires access to the control-plane database, not an API token:

```bash filename="extract the node SSH key (control-plane database)"
psql "$DATABASE_URL" -At \
  -c "SELECT data FROM terraform_state.states WHERE name = '$CLUSTER_ID'" \
  | jq -r '.outputs.ssh_private_key.value' > cluster.pem
chmod 600 cluster.pem
```

Connect as **`ubuntu`** — the same user the provisioner itself uses:

```bash filename="ssh to a node"
ssh -i cluster.pem ubuntu@<node-ip>
```

`kubectl` on the nodes requires sudo: `sudo k3s kubectl get nodes`.

The key is deleted together with the Terraform state when the cluster is destroyed, so extract it while the cluster still exists. Treat it with the same care as the cluster JWT — it is root-equivalent access to every node.

### Scaling a cloud-provisioned cluster

```bash filename="scale cluster"
curl -X POST https://api.your-domain.com/api/v1/clusters/$CLUSTER_ID/scale \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"desired_node_count": 5}'
```

kubenest runs a Terraform apply to add or remove EC2 instances and registers the new nodes with the existing Kubernetes control plane. BYOC clusters are not affected by the scale endpoint — node management for those clusters is handled outside kubenest.

## Connection state reference

| State | Meaning | Possible next states |
|-------|---------|---------------------|
| `pending` | Cluster record created; no action taken | `provisioning`, `awaiting_operator` |
| `provisioning` | Cloud provider creating infrastructure | `awaiting_operator`, `error` |
| `awaiting_operator` | Infrastructure ready; operator not yet connected | `connected`, `error` |
| `connected` | Operator has an active WebSocket session | `disconnected` |
| `disconnected` | Hub lost the session; operator may be restarting | `connected` (auto-reconnect) |
| `error` | Unrecoverable error; see `message` field | — |

The operator implements exponential backoff reconnection. Most `disconnected` states resolve within 30–60 seconds without user intervention.

## Deleting a cluster

<Callout type="warning">
**Deletion needs the org `admin` role, and projects block it.** `DELETE /clusters/{id}` returns `409` while any project still exists on the cluster, naming the projects that block it, on both the BYOC and the cloud-provisioned path. Delete the projects first — there is no force or cascade parameter.

The guard covers projects, not apps or addons: those live inside a project, so removing the projects removes them. Beyond the project check there is no confirmation step, and for a cloud-provisioned cluster the call that succeeds destroys real infrastructure.
</Callout>

What deletion does depends on how the cluster was created:

- **BYOC:** the cluster record is deleted immediately. Nothing on the cluster itself is touched — the operator keeps running, workloads keep serving, namespaces stay. Only the control-plane record, and every project record under it, disappears.
- **Cloud-provisioned:** the backend launches a `terraform destroy` that tears down the EC2 instances, VPC, and associated resources, regardless of what is deployed on them. The cluster status moves to `destroying`; when the destroy succeeds, the cluster record and its project records are removed, and the Terraform state — including the node SSH key — is deleted with it.

**For BYOC clusters**, clean up in this order. The ordering is advisory — the API does not enforce any of it:

```bash filename="BYOC cleanup"
# 1. Uninstall the operator from the cluster
helm uninstall kubenest-operator -n kubenest-system

# 2. Optionally remove the namespace
kubectl delete ns kubenest-system

# 3. Delete the cluster record from the backend
curl -X DELETE https://api.your-domain.com/api/v1/clusters/$CLUSTER_ID \
  -H "Authorization: Bearer $TOKEN"
```

## Troubleshooting

**Operator pod is in CrashLoopBackOff.** The most common cause is a malformed or expired cluster JWT. Check the pod logs for `"invalid token"` or `"token expired"`. Issue a new token via `GET /api/v1/clusters/{id}/install-command`, set it as `kubenest.jwtSecret` in your values file, and run `helm upgrade` — or update the `kubenest-operator-token` Secret and restart the pod, if you created one.

**Cluster stuck in `awaiting_operator` after operator install.** The operator is not reaching the hub. Verify:
- The pod is `Running` (not `CrashLoopBackOff`).
- The `kubenest.backendURL` value starts with `wss://` (not `ws://`) and includes the `/ws/operator` path.
- Outbound HTTPS/WSS traffic from the cluster to the hub URL is permitted by your network policy.
- DNS resolves the hub URL from inside the cluster: `kubectl exec -n kubenest-system <operator-pod> -- curl -I https://hub.your-domain.com`.

**`connected` then immediately `disconnected`.** This is usually a heartbeat timeout. The operator sends a heartbeat every 30 seconds; the interval is fixed in the operator and is not configurable through Helm values. Check for high CPU or memory pressure on the operator pod that might delay heartbeats.

**Provisioning stuck in `provisioning` for more than 20 minutes.** Check the provisioner job logs on the backend pod:

```bash filename="check provisioner logs"
kubectl logs -n kubenest-system \
  -l app.kubernetes.io/name=kubenest-backend \
  --tail=50 | grep provisioner
```

Common causes: AWS credentials lack the required IAM permissions, the requested instance type is unavailable in the region, or a VPC limit has been reached.
